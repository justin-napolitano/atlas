# Working tabs and project navigation

The sidebar is a project tree. The active project exposes Sources, Questions, and Notes. Each destination has its own creation action. Occasional reading tools live below the Sources catalog; comparison, questions, notes, bookmarks, and passage research actions remain with the reading. The catalog also provides access to the project's saved bookmark. There is no separate Explore menu in the sidebar.

Opening a research record adds a working tab. Each record has one tab; changing its edition or selected passage updates that reading. Questions and Notes each have one working tab per project, preserving their selected entry, filters, editor mode, and contained source pane. Choosing their sidebar link resumes the open workspace. Explicit new-entry and search-result actions still select the requested entry.

The browser keeps up to four warm working pages, suspending the least recently used clean pages while retaining lightweight tab descriptors. Dirty, saving, failed, and conflicting work stays mounted; protected work can exceed the target, with a visible explanation rather than silent eviction. Save or discard changes to release those pages. A tab with unfinished work stays open when Close is pressed and directs you to its save/export/discard actions. Closing a clean tab releases its mounted page without deleting research.

Tabs show Unsaved, Saving, Save failed, or Conflict beside the actual work. A confirmed actual-note save clears that status; a private recovery acknowledgement does not pretend the note is saved. Notes/Questions expose server-backed Unfinished work separately. Source-linked capture/import drafts carry their source/project identity so a different reading cannot be treated as their owner.

Tab switching captures scroll offsets and source selections as lightweight DOM paths and text, not retained DOM nodes or Range objects. Selection restores only if the text still matches. Clean suspended pages reopen through their normal source/edition/passage routes and APIs; saved immutable anchors remain authoritative if the changed/loading layout cannot reproduce a viewport. This is not cross-device pixel-perfect scroll synchronization.

Tab metadata, scroll, selection, and unsaved content are not written to localStorage or sessionStorage. Reload starts a fresh set of tabs while the URL reopens the selected saved reading or entry. Automatic owner-backed writing recovery is described in [durable-writing.md](durable-writing.md); only acknowledged copies are durable. This change does not provide cross-device tab or scroll sync. Saved project content retains its existing PostgreSQL behavior; the loopback review adapter still saves only on this Mac.

Background notebook responses can update their own tab title and entry link, but only the active workspace may replace the current URL. Saved concept data, record connections, and notebook/question indexes refresh on returning to a tab without resetting writing drafts. Reading text remains tied to its saved immutable version. Notebook DOM queries are scoped to their own editor, and reading heading and record-note IDs are unique across mounted pages. New projects and private writing remain separate from explicitly published research.

`node scripts/review-working-cache.mjs` exercises three cycles through 30 synthetic readings, bounded mounted DOM, protected overflow, release after clearing protection, inactive effect cleanup, scroll restoration, and closed-page cleanup. DOM observations after explicit test garbage collection describe retained nodes in that harness, not a production heap limit or measured CPU/fan improvement.
