# Reading and writing as equal destinations

Current reading/editing and automatic-save behavior is described in [document-first-workspace.md](features/document-first-workspace.md). The later compact explorer replaces the original prose-heavy notebook index with project/collection folders and note titles; recovery, Trash, and advanced filters remain in Notebook tools.

The owner workspace has two persistent destinations: **Reading** and **Notebook**. The notebook is a project-level writing surface that opens directly with `/workspace.html?project=PROJECT_ID&view=notebook`. It does not require a source or a reading selection. The existing source-based annotation and personal-notebook authorities remain separate.

## Flow

1. Open **Notebook** in the header. The source library gives way to a note index and a writing page. **Library** still opens project selection and reading tools. Search and agent briefs remain available in the shared header; theme and publication are in **More**.
2. Choose **New note**, enter a title, and write. Notes use the existing `note` thought type and store no source/document/passage anchor by default. Questions, interpretations, objections, and located source claims retain their distinct types. The explicit **Note on this reading** action makes an optional source anchor available.
3. **Save note** or Cmd/Ctrl+S confirms a save through the existing notebook API. The toolbar distinguishes unsaved edits, a pending save, a confirmed revision, and an uncertain acknowledgement. The existing UUID retry, revision conflict comparison, withdrawal/history, and in-page draft retention continue to apply. This pass does not add autosave or offline durable drafts.
4. Open **Connections** to search actual project research. Choose a result, explain the connection, add it, and save the note. Search does not write anything. Notebook thoughts link as entries, saved passage notes/definitions as annotations, concepts as concept records, and documents as their source records (explicitly labeled). No exact passage is invented for a document search result. ID-based linking remains an advanced option.
5. Open **Note details & history** for withdrawal, revisions, stable IDs, and Markdown export. Export includes only the last confirmed save and its source/link IDs; unfinished edits are explicitly excluded. Saved entry selections update the notebook URL for direct reopening.
6. On a phone, the note index and editor are separate views; **All notes** returns to the index. Desktop retains both side by side. Notes store portable Markdown source, with **Write / Preview** modes, a readable measure, visible keyboard focus, RTL-aware text fields, and a sticky save toolbar.

## Markdown and the note graph

The rendered preview uses pinned [react-markdown](https://github.com/remarkjs/react-markdown) and [remark-gfm](https://github.com/remarkjs/remark-gfm) for CommonMark plus tables, task lists, strikethrough, autolinks, and footnotes. Fenced code is displayed as inert text; there is no code execution. Raw HTML is not enabled. Executable/data/protocol-relative URLs are refused. Remote images require an explicit load click and omit the referrer. This is not arbitrary MDX/HTML, a plugin runtime, LaTeX, or Mermaid rendering.

`[[Note title]]` resolves only when the full loaded project notebook contains exactly one matching active title. `[[NOTE_ID|Display label]]` preserves identity across renames. **Linked notes & backlinks → Insert a wiki link** inserts that stable form. Links inside code, existing Markdown links, HTML, or escaped brackets do not become wiki edges. Unresolved and duplicate titles remain visible without invented links.

**Note graph** reuses the existing interactive network explorer: local neighborhoods, depth, pan/zoom, explicit directed edges, text alternatives, graph analysis, and opening the actual note. The graph projects saved `entry` links and Markdown wiki links; it never promotes notes to reviewed claims or edits canonical RDF. Source/annotation/concept links remain in Connections; they are not falsely represented as notebook entries. Backlinks are derived from the same saved-note projection. Current unsaved Markdown is previewable but does not create saved graph edges.

The signed-owner `GET /v1/notebook/network?project_id=…&limit=200` reads a bounded current-state projection of active notes, without actors, history, or source document text. It requires owner authentication and returns no-store responses; the public runtime does not register it. There is no migration or second graph authority. The graph loads only when requested, or when preview/backlinks need it. Saving refreshes a previously loaded projection. When more than 200 notes exist, the limit is visible, backlinks are explicitly incomplete, and title-based resolution is disabled; loaded stable IDs still work. This limit needs pagination/server graph retrieval before claiming a complete large notebook network.

## Validation and limits

`node web/scripts/review-notebook.mjs` exercises real compiled components against a labeled synthetic API, including independent note creation, explained search-based connections, uncertain saves, retries, conflicts, history, late acknowledgements, mobile navigation, GFM preview, inert hostile content, saved wiki navigation, backlinks, and the actual saved note graph. `review-workspace.mjs` and `review-research-tools.mjs` retain the reader, source, publication, search, and brief regressions. These checks and screenshot inspection do not establish complete accessibility compliance or hosted two-device behavior.

This is one notebook per existing research project, with independently addressable notes. It does not introduce a hierarchy of notebook collections, WYSIWYG editing, automatic Obsidian synchronization, model execution, migrations, or hosted deployment. The new Markdown dependencies and private network retrieval surface require human review before live rollout. Live owner writing still requires the configured authenticated PostgreSQL runtime; the loopback review adapter remains local-only.
