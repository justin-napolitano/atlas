# Private unfinished writing

Independent notebook/question recovery uses `/v1/notebook/draft` (GET/PUT) and `/v1/notebook/drafts` (GET, project-scoped cursor pagination). These owner-only endpoints are separate from confirmed notebook entry creation and editing. Untitled and empty drafts are valid; actual note saves still require title/body and explicit confirmation.

Migration `0016_notebook_recovery.sql` adds private current rows and immutable revision history. Run the existing migration and role-grant workflow before deploying the updated owner service. Publisher roles receive no access. The public service does not register these routes, and the explicit publication projection does not select recovery rows.

Each recovery identity has an immutable project, entry/creation identity, original source/edition/passage anchors, and historical baseline revision. Server-derived baseline snapshots allow comparison after another session changes a note. Writes use expected revisions; exact immediate retries are idempotent, and conflicting values return the current copy rather than overwrite it. New writing keeps its original note-creation UUID to avoid duplicate actual notes after recovery.

Recovery never marks a source read, approves scholarship, publishes writing, or updates a confirmed note. Active copies are retained until explicitly discarded; discard hides the current copy while retaining private revision history. No automatic expiry or permanent purge is introduced. Backup retention remains part of the hosted operator policy.

## Editor behavior

Notebook notes/questions and supported record/margin/capture editors enqueue private recovery after 800 ms of quiet, with a maximum 5-second delay while typing. Writes are serialized. A delayed acknowledgement cannot replace newer writing; a failed request remains frozen for explicit retry before the queued newer version is sent. A conflict can be compared and forked into two recovery copies. Confirmed-note saving remains an explicit action. Source captures retain their creation identity so recovery can detect an annotation that was already committed.

Migration `0018_capture_recovery_classification.sql` allows a pending capture to change between reading note, term candidate, and citation candidate under the same recovery/capture identity. Its exact source selector and baseline remain immutable; an already saved annotation's capture type cannot change through recovery. This avoids treating an ordinary composer classification change as a different source or duplicate annotation. Update owner grants for the narrowly allowed recovery `capture_kind` column.

Notes and Questions expose **Unfinished work** with project-scoped private copies, including untitled writing. Inspect a copy before recovering it. Recovery does not replace another local draft; changed confirmed baselines enter the existing explicit comparison flow. Recovering a new note retains its creation UUID, and explicitly saving it creates the actual note once. Confirmed saves discard the active notebook recovery copy through the same serial queue; private revision history remains.

Statuses distinguish unsaved editor changes, recovery waiting/saving/confirmed, actual-note saving/confirmed, and failed/conflicting writes. Keystrokes before the first acknowledgement are not crash-safe. Page-hide/visibility-change flushes are best effort, not an offline durability guarantee. Private writing and authentication are not persisted to localStorage or URLs. Keep the page open when recovery fails or owner authentication expires, then retry after reconnecting/signing in.

Security review scope: private data access and three owner API routes, with existing IAP/origin/write-header checks unchanged. Boundary tests verify wrong owner/origin, extra fields, no-store responses, and public route absence. Real PostgreSQL tests cover independent sessions, retries/conflicts, immutable baselines/history, and publisher grants. Local runs without an isolated PostgreSQL DSN skip those integration tests; the PR's PostgreSQL 17/18 checks provide the actual database verification. Human review of the API/grant changes remains required before production release under the repository's applicable security guidance.
