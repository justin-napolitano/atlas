# Explicit public research snapshots

Publication is a separate axis from scholarly review and personal reading progress. The owner chooses exact records and relations, inspects a sealed preview, and approves its digest. The owner screen and PostgreSQL/API approval/withdrawal are implemented; the immutable image exporter/build/deploy, cache replacement, rollback policy, and hosted verification remain follow-up work in #41. No real research is approved by implementation tests.

## Owner screen

Choose **Publish research** from the reading workspace, or open `/publish.html` on the same authenticated owner origin. Select a project and search/browse its records. Check individual records; summaries and bibliography are excluded until you opt in for each one. Private-only kinds and withdrawn records are disabled. Selected records stay in this page's memory when changing projects or searches; the leave warning covers unsaved selections and private rationale text. Nothing is written to localStorage except theme and pane-width preferences.

Choose **Find connections between selected records**, then check the recorded relations you intend to publish. The private owner endpoint is `POST /v1/publication/relations` with `project_id` and `record_ids`; it returns at most 300 project-scoped, active relations with endpoint titles and full predicates, omitting raw provenance. Both endpoints must be selected. A truncated result says so; narrow the selection to inspect fewer relations. Removing/changing the selected records clears relation choices so dangling links cannot survive silently. This picker checks recorded structure, not whether a relation is a sound scholarly assertion.

**Make private preview** saves a sealed snapshot and moves focus to its readable records, included connections, and complete public JSON/digest. Its authenticated link can reopen the same preview after reload or on another machine. A reopened preview does not approve itself. Review all included content and actual source-review limits, supply a private publication rationale, then explicitly acknowledge privacy/attribution/quotation-rights review before **Approve this snapshot** becomes available. Editing selection/options invalidates that preview and acknowledgement. The screen labels approval separately from a completed public-site build.

A source/head conflict requires a refreshed approval status and a newly inspected preview; unrelated picker actions cannot clear that requirement. An unconfirmed network response retains the same preview/digest/head revision/rationale for an exact retry. Approval of the already-current snapshot is disabled. Withdrawal has its own private rationale and explicit revision-specific acknowledgement; an unconfirmed withdrawal requires a head refresh before retrying. Neither approval nor withdrawal claims that deployed images or cached copies changed immediately.

## Owner API flow

All `/v1/publication/*` routes use the existing signed IAP sole-owner boundary. Mutations require JSON, `X-Research-Write: 1`, and the configured origin when supplied. The server derives the actor from verified identity. Public mode registers none of these routes.

1. `GET /v1/publication/head?project_id=…` returns the current public revision, status, and snapshot ID. A project with no publication has revision zero and private status.
2. `POST /v1/publication/previews` takes `project_id`, `selections` (1–100 objects with `record_id`, `include_summary`, `include_bibliography`), and up to 300 explicitly selected `relation_ids`. Both inclusion flags default false. Both endpoints of each selected relation must be included. Missing, deleted, withdrawn, cross-project, duplicate, or private-only record kinds fail.
3. Inspect the returned **complete payload**, `id`, and `payload_sha256`. `GET /v1/publication/preview?project_id=…&preview_id=…` reopens that exact preview; it does not return internal inputs or actor metadata. Review privacy, attribution, quotation rights, source roles, and the actual limitations shown. The preview digest uses PostgreSQL's `jsonb::text` UTF-8 representation; clients submit the provided digest unchanged. It is an approval token for those stored bytes, not a portable JSON canonicalization standard or proof of scholarly correctness.
4. `POST /v1/publication/approve` takes `preview_id`, `expected_sha256`, the current head's `expected_revision`, a private `rationale`, and literal JSON `rights_checked: true`. Integers, strings, false, and omitted acknowledgements fail validation. The server locks the selected inputs, checks the sealed source state, and atomically creates the public snapshot, private event, and new head. No research review status changes. A stale digest/source/head yields 409: reload the head and make a new preview, never silently approve changed content. An identical retry of a successful current approval returns the existing head without creating another event.
5. `POST /v1/publication/withdraw` takes `project_id`, `expected_revision`, and a private rationale. It advances the head to withdrawn with no active snapshot. History and old immutable snapshots remain retained. A stale request conflicts. The same currently withdrawn revision is a no-op, rather than another withdrawal event.

## Projection boundary

Only the selected project title/ID, selected record IDs/titles/types/origins/revisions and actual review states, explicitly included summaries/bibliography, and selected relation IDs/directions/predicates/states enter the payload. Bibliography parsing uses a fixed set of RDF predicates for citation, creator, scope, role, locator, source links, and original review labels. Those labels retain their original limited scope; visibility approval is not external peer review. Source links with credentials, query strings, control/space characters, localhost/internal names, or nonglobal literal IP addresses are omitted. This is a conservative link filter, not source authentication or DNS verification. No imported HTML is executed and no remote context/source is fetched.

The graph remains derived from canonical RDF while the project retains that authority. Publication does not perform the graph-authority cutover. Imported canonical snapshot SHA-256 checksums, full predicates, stable IDs, and selected record revisions preserve traceability without inventing scholarly support; the owner must select enough located evidence and attribution for public readers. Raw relation provenance and importer identities stay private. The current payload has no discovery candidates: an automatic bibliography publication policy is separate work.

Personal notes, reading/Keep/Skip state, imported reading excerpts, passage comments, arbitrary record attributes, relation provenance internals, user/service identities, and logs are excluded. Explicit selection still exposes the selected titles and, when requested, summaries and bibliography: inspect their contents, since no program can certify that free text contains no private information or that its interpretation is correct. Private-only `note`, `annotation`, `passage`, generic `record`, and `activity` kinds are refused by this initial projection policy. A public passage representation will need its own rights/context policy.

Private previews retain the complete selected source rows for exact staleness checks. They may contain private attributes and actor metadata internally, remain readable only through the owner SQL role, and must stay out of build logs and public archives. Payloads are capped at 1 MB by the projector and 2 MB in PostgreSQL's serialized representation. Preview retention/cleanup and multi-part corpus releases are not implemented yet.

## SQL authority and public delivery

Run migrations as the migration identity, then rerun the explicit SQL grant bootstrap. The owner receives private preview inserts/reads and execution of exactly four registered functions: input read, head read, approval, and withdrawal. It receives no direct public-schema usage/write, no preview update/delete, and no event/history mutation. A database trigger rejects extra/nested private fields, identity/review-state changes, duplicate/dangling nodes and relations, unsafe source links, and changed inputs even for direct preview inserts. Fixed `SECURITY DEFINER` functions use qualified tables and a fixed search path; PUBLIC function execution is revoked. This boundary requires security-sensitive human review before release.

The publisher SQL login reads only public snapshot and head tables. A builder must select **only the currently published head**; retained historical rows are not an invitation to republish withdrawn versions. The transitional public API likewise reads only active heads and checks its SQL identity's private access and table/column write powers before each data read. Anonymous mutation requests and owner-publication routes are absent from public mode.

Changing a database head is **not** proof that an already deployed static image or a reader's cached copy has changed. The chosen production design still requires an immutable public image with no database identity, an approved-head exporter, last-good build retention, withdrawal replacement/cache handling, and guarded rollback. Never claim global erasure or a completed deployment from an API withdrawal alone. See [publication threat model](publication-threat-model.md) and [ADR 0003](adr/0003-immutable-public-delivery.md).
